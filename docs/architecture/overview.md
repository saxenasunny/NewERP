# Architecture Overview

Status: living document. Update it when a phase changes the structure.

Source of truth for product scope: [`docs/LMS_BUILD_SPEC.md`](../LMS_BUILD_SPEC.md).

## 1. Shape of the system

A **modular monolith**: one Next.js application, one PostgreSQL database, one
deployment unit. Modules are separated by directory and by an explicit service
boundary, so a module can be extracted later without rewriting the product.

```
Browser
  │
  ▼
Next.js App Router (app/)
  │  Server Components render reads; Server Actions / Route Handlers handle writes
  ▼
modules/<domain>/  ← application services (validation, authorization, transactions)
  │
  ├── lib/auth         (Better Auth config, session, account context)
  ├── lib/permissions  (central permission catalogue + checks)
  ├── lib/tenancy      (request-scoped actor + tenant resolution)
  ├── lib/db           (Prisma client, transactions)
  ├── lib/audit        (append-only audit events)
  ├── lib/mail         (email adapter; development outbox)
  └── lib/rate-limit   (shared database-backed limiter for Server Actions)
  │
  ▼
PostgreSQL
```

### Rules that keep the monolith modular

1. Page components and route handlers do not contain business rules. They parse
   input, call a service, and render the result.
2. A service receives an **actor** (authenticated user + tenant membership) and
   never derives identity from a request body, query string, or client header.
3. A service validates input with Zod at its boundary, even if the caller is
   another service.
4. Reads and writes of tenant-owned tables always carry `tenantId`. Where a
   nested resource is addressed by ID alone, the service first loads it scoped to
   the actor's tenant and returns "not found" for a foreign tenant's row.
5. Multi-step writes run in a Prisma interactive transaction.
6. Retryable, consequential actions (submission, quiz finalisation, certificate
   issuance, imports) accept an idempotency key with a database uniqueness
   guarantee.
7. Audit events are appended in the same transaction as the change they describe.

## 2. Tenant model

- A **tenant** is an institution. All learning data belongs to exactly one tenant.
- A user is global (`users`), and gains access through a **membership** in a
  tenant plus **role assignments** scoped to that tenant (and optionally to a
  department, programme, or course offering).
- The active tenant comes from the authenticated session, not the URL. A user who
  belongs to several tenants switches explicitly; the switch is validated
  server-side against their memberships. `resolveActor()` implements this today:
  one active membership is inferred, several require an explicit selection, and
  no active membership, suspended tenant, or deactivated user is denied.
- Tenant-owned rows carry a `tenant_id` column even when it is derivable through
  a parent, so that every query can be scoped without joins and so cross-tenant
  mistakes surface in review and tests.

Details and test obligations:
[ADR 0002](../decisions/0002-tenant-isolation-and-authorization.md).

## 3. Authorization

Deny by default. Two checks are always required:

1. **Permission**: does the actor's role set include the capability
   (`courses.publish`, `grades.update`, ...)? The catalogue
   (`lib/permissions/catalogue.ts`) is code-owned and mirrored into the database
   for auditing; role definitions live beside it and seed the database.
2. **Resource scope**: is this specific record inside the actor's tenant and,
   where applicable, their assigned department/programme/course? Course-level
   access comes from `course_instructors` or `enrolments`, not from a role alone.

UI hiding is never the control. Every server entry point calls the same
permission helper; tests cover both allowed and denied paths.

## 4. Rendering and caching

Cache Components / `use cache` is intentionally **off**. Most pages read
tenant-scoped data under a session cookie; an accidentally cached response is a
cross-tenant data leak, and this product has no high-traffic public pages that
need the optimisation. Reads are dynamic and go through the database per request.
See [ADR 0003](../decisions/0003-rendering-and-caching-policy.md).

## 5. Data conventions

- Timestamps: `timestamptz` in UTC. Rendering converts to the institution's time
  zone; the browser never supplies the authoritative deadline or timer.
- Marks, weights, and percentages: `Decimal` (PostgreSQL `numeric`), never
  floating point, and never accepted as precomputed values from the client.
- IDs: CUID/UUID strings generated by the database layer; institutional IDs
  (student numbers) are stored as text.
- Files: bytes live in private object storage; PostgreSQL stores metadata and
  object keys. Downloads go through an authorised route, never a public bucket
  URL.
- Soft deletion is introduced only where a record must remain auditable; the
  hiding rule is part of the query helper rather than ad-hoc filters.
- Every table with mutable academic state has `created_at` / `updated_at`.

## 6. Environments and configuration

| Concern      | Development                       | Test                                   | Production                       |
| ------------ | --------------------------------- | -------------------------------------- | -------------------------------- |
| Database     | Local PostgreSQL (docker compose) | Separate PostgreSQL database/schema    | Managed PostgreSQL               |
| Env loading  | `.env.local` (gitignored)         | Explicit env passed by the test runner | Secret manager                   |
| Email        | Development outbox (no delivery)  | Captured outbox                        | Provider adapter (unconfigured)  |
| File storage | Local private directory `.data/`  | Temporary directory per run            | S3-compatible private bucket     |
| Jobs         | In-process runner for dev         | Synchronous test runner                | Durable queue (not yet selected) |

`lib/env.ts` validates server configuration lazily and fails closed with the
**names** of invalid variables. Secrets are never logged, rendered, or committed.

## 7. Observability

- Every request gets a request ID (accepted from `x-request-id` only if it is a
  safe opaque token, otherwise generated) that is attached to structured logs and
  API error bodies. `proxy.ts` adopts/generates it; handlers reuse it.
- `GET /api/health` is a liveness probe. `GET /api/health/ready` pings PostgreSQL
  and returns 503 when it is unreachable; storage readiness arrives with the
  storage adapter.
- Audit events record actor, tenant, action, resource, before/after values,
  reason, request ID, and timestamp for sensitive operations.

## 9. Current implementation state (Phase 6)

- Identity and tenancy from Phase 2–3: `tenants`, `institutions`, `users`,
  `tenant_memberships`, `roles`, `permissions`, `role_permissions`,
  `user_role_assignments`, `audit_events`, `sessions`, `accounts`, `verifications`,
  `invitations`, `email_messages`, `rate_limit_buckets`; Better Auth sign-in/sign-out
  and password reset; invitation-only account creation; scoped role assignment;
  deactivation with immediate session revocation; tenant-scoped people directory
  and API; request IDs; readiness probe.
- Academic structure: `academic_years`, `terms`, `departments`, `programmes`,
  `cohorts`, `sections`, `cohort_members`, plus `institutional_id` on memberships.
  Terms must sit inside their year; the database enforces the natural keys.
- Catalogue and delivery: `courses` (reusable, tenant-scoped by code) and
  `course_offerings` (one delivery in a term, optionally for a section), with
  `course_instructors` and `enrolments` hanging off the offering. Status enums make
  archive/withdraw the normal lifecycle and keep history readable.
- Imports: `import_jobs` and `import_rows` store the parsed file, every row's
  verdict, and the commit counts. Preview writes nothing else; commit applies valid
  rows by natural key inside one transaction and records an audit event.
- `getAccountContext()` is the single place where a session becomes an actor with
  a tenant, roles, and permissions. Pages and route handlers call it; they never
  trust a client-supplied tenant or role.
- `modules/academics/structure-service.ts` owns the structure hierarchy and
  `modules/academics/course-service.ts` owns catalogue, offerings, instructors, and
  rosters. Both take an `AccountContext` and check permissions themselves, so an
  action or route handler cannot bypass them.
- Course content: `course_modules`, `content_items`, `module_prerequisites`,
  `content_progress`, and `learning_events`. Content belongs to a delivery
  (offering), so the same catalogue course can run differently each term.
- `modules/content/content-service.ts` owns authoring (modules, items, ordering,
  publishing, copying, file storage) and `modules/content/delivery-service.ts`
  owns the learner view, progress, and the file-authorisation check. Visibility
  rules live in `modules/content/visibility.ts` as pure functions, so the same
  rule can be unit-tested and reused by the download route.
- Assignments: `assignments`, `assignment_submissions`,
  `submission_text_versions`, `submission_file_links`, `rubric_criteria`,
  `rubric_criterion_scores`, `grades`, `grade_feedback`, `grade_change_events`.
  There is one submission row per learner per assignment (enforced by a unique
  index), and text versions are append-only, so a resubmission keeps its history.
- `modules/assignments/rules.ts` owns the pure rules (window, lateness, the
  submission gate, learner status, grade visibility, percentages).
  `assignment-service.ts` owns authoring, publication, and the rubric;
  `submission-service.ts` owns drafts, receipts, retries, history, and private
  submission files; `grading-service.ts` owns the queue, rubric scores, draft
  grades, release, overrides, and grade change events. Grades default to draft
  and are never shown to a learner until released.
- Files are private. `lib/storage` exposes one adapter interface with a local
  (development/test) implementation and an S3-compatible one that is installed
  but unverified; downloads are proxied through `/api/v1/content/[itemId]/file`,
  which repeats the visibility check before reading bytes.
- Sent email is captured, not delivered: development renders it at `/dev/mail`,
  production marks it undelivered because no provider is configured.
- Deliberately absent: quizzes, gradebook, attendance, OBE, and certificates.
  No placeholder screens exist for those modules.

## 10. Non-goals for the current architecture

- Microservices, message brokers, or a separate API service before load requires
  it.
- Native mobile apps; the web app is responsive and installable later.
- AI-assisted authoring, proctoring, or SCORM/LTI before the core workflows are
  stable and tested.
